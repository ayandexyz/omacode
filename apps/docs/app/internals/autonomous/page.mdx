# Autonomous runs

`freecode night` is the implemented unattended-work feature. It is built
through Phase 5 of `docs/specs/2026-09-28-overnight-runs.md`: it runs short agent iterations, commits successful work to
a dedicated `night/*` branch, records decisions, and produces a report for
human review.

The shared manifest types, budget calculations, and atomic run storage are the
foundation beneath `freecode night`. The overnight specification is the current
design and implementation record.

## The beginner mental model

Do not think “leave one agent conversation running forever.” A night run is a
series of small, bounded attempts:

```text
Your objective
   ↓
Fresh agent session completes one small step
   ↓
Verify it, commit it, and record the result
   ↓
Start the next fresh session—or stop for a limit, failure, or success
   ↓
Morning report + a branch for you to review
```

This is **bounded autonomy**: the agent may work without you watching, but it
is constrained by limits, a permission envelope, Git isolation, and an audit
trail. A passing verification command is evidence, not approval; FreeCode never
merges the branch for you.

## What `freecode night` does

```bash
freecode night "reduce the TUI render cost" --until 07:00 --verify "pnpm test"
```

For each iteration, FreeCode:

1. Starts a fresh session with the objective, notes from earlier iterations,
   and a `finish_iteration` tool.
2. Lets the model work within the unattended permission envelope.
3. Runs `--verify`, if you supplied it.
4. Commits a successful, verified step to `night/<objective-slug>`.
5. Resets failed or incomplete work, records why, and either retries or stops.

The **orchestrator**, not the model, owns commits, resets, limits, and the final
stop decision. The model reports its result through `finish_iteration`; it
cannot directly commit, push, switch branches, or declare an unchecked change
successful.

## Safety boundaries

| Boundary | What it protects |
| --- | --- |
| Limits | stops at `--until`, `--max-iterations`, `--max-usd`, failure, or cancellation |
| Fresh sessions | prevents one enormous context window from accumulating overnight |
| Dedicated branch | keeps work off your current branch and never merges automatically |
| Optional worktree | `--worktree` lets the run use a separate checkout while you keep working |
| Permission envelope | refuses dangerous Git, publishing, remote, and system-changing commands |
| Optional sandbox | on Linux, Bubblewrap confines unattended shell writes to the run tree by default |
| Verification gate | `--verify` must exit successfully before an iteration is committed |
| Report and logs | lets a person inspect decisions, commits, failures, waits, and remaining questions |

The envelope is a guard rail, not a complete security sandbox. It blocks known
irreversible and outward-facing commands, while the branch/worktree, reset
policy, and optional Bubblewrap sandbox provide separate layers of protection.

## Limits, failures, and quota waits

The orchestrator stops for an objective being met, an iteration or cost limit,
a deadline, repeated failures, a permanent provider error, cancellation, or a
hard interruption.

A usage-window quota is treated differently from a bad API key or exhausted
credits. When the provider gives a future reset time, FreeCode can wait and
retry the **same** iteration. It caps both one wait and total wait time; it can
also retry the first spent window using `--fallback-model provider/model`.
Credits and authentication failures are permanent errors because waiting is not
expected to fix them.

This is **failure classification**: different error categories get different
recovery behavior instead of one blind retry rule.

## Starting, observing, and stopping a run

```text
freecode night "<objective>" --until 07:00
freecode night status [run-id-or-branch]
freecode night report [run-id-or-branch]
freecode night list
freecode night stop [run-id-or-branch]
```

`night stop` writes a cancellation request to the manifest. The runner checks
it at an iteration boundary rather than killing itself mid-write. `status` and
`list` reconcile a manifest whose recorded process id has died, marking the run
as crashed instead of falsely reporting it as still running.

`--detach` starts a detached worker so the terminal can close. `--at` schedules
a detached worker for a future local time, duration, or ISO timestamp. Detached
workers use a dedicated worktree, write their output to `worker.log`, and can
be observed with the same status/report commands.

## Storage and the morning report

Each run stores durable state under:

```text
~/.freecode/runs/<run-id>/
├── manifest.json       status, limits, usage, branch, process details
├── notes.md            carry-forward notes for later iterations
├── iterations.jsonl    completed iterations and quota waits
├── decisions.jsonl     unattended asks, denials, choices, needs-human items
├── report.md           review summary; can be regenerated
└── worker.log          detached worker output, when applicable
```

`manifest.json` is written atomically (temporary file, then rename), so readers
do not see a half-written document. The report is a **pure fold** over the
manifest and JSONL logs. That means `freecode night report` can regenerate a
report after a crash instead of relying on a single final write that may never
have happened.

The report tells you what happened; it does not claim the work is correct. It
includes commits, verification status, failures, quota waits, decisions, items
that need a human, and commands to inspect or discard the `night/*` branch.

## What is not included

`freecode night` is explicitly user-started. It is not an ambient daemon that
decides to edit projects on its own schedule. It does not merge to a default
branch, force-push, or turn verification into human approval.

## Interview vocabulary

- **Bounded autonomy:** unattended work that has explicit resource and safety
  limits.
- **Orchestrator:** a controller that coordinates iterations and owns policy
  decisions instead of leaving them to the model.
- **Fresh-session iteration:** start each step with a clean session plus a
  concise handoff, limiting context growth and carrying only useful learning.
- **Permission envelope:** a stricter policy used only while nobody is present
  to approve actions.
- **Defense in depth:** branch isolation, permission checks, verification,
  limits, sandboxing, and audit logs overlap rather than relying on one guard.
- **Atomic write:** write a temporary file then rename it, preventing partial
  persistent state.
- **Pure fold:** derive a report from durable events; regenerate it reliably
  after a crash.
- **Human-in-the-loop review:** automation prepares committed work and evidence;
  a person still reviews and approves it.
