# Effect runtime & DI

FreeCode uses [Effect](https://effect.website) for part of its dependency
wiring. In plain English: code says what it needs—a session store, hooks,
memory, and so on—and one central place chooses the real version in production
or a safe replacement in a test.

Think of a coffee machine. The machine needs “water,” not a particular tap. In
the same way, the agent loop needs “a session store,” not a hard-coded file on
your laptop. This is **dependency injection (DI)**: dependencies are supplied
from outside instead of being constructed invisibly inside the consumer.

```text
Agent loop asks for SessionStoreTag
              ↓
Live layer     → ~/.freecode session files
Test layer     → a temporary test directory
```

The benefit is practical: tests can exercise a real agent loop without writing
to your real sessions. This is a focused DI boundary, not a claim that every
module in FreeCode has been converted to Effect.

## The four files

The implementation lives in `apps/core/src/effect/`:

| File | Job |
| --- | --- |
| `context.ts` | names the services the runtime can supply |
| `layers.ts` | connects those names to live or test implementations |
| `runtime.ts` | creates, shares, and disposes a runtime |
| `loop-health.ts` | contains the pure policy for detecting a likely stuck loop |

## Tags: names for dependencies

A **context tag** is a typed label for one service. It contains no business
logic; it simply says, “when something asks for this label, give it a value
that matches this contract.”

```ts
export class SessionStoreTag extends Context.Tag("freecode/SessionStore")<
  SessionStoreTag,
  SessionStore
>() {}
```

`context.ts` defines nine tags:

- `HookRuntimeTag`
- `ToolOrchestratorTag`
- `SessionStoreTag`
- `BusTag`
- `ProviderRegistryTag`
- `MemoryFactoryTag`
- `RecorderFactoryTag`
- `SessionManagerTag`
- `RecoveryManagerTag`

Two are **factories**, not shared objects. `MemoryFactoryTag` and
`RecorderFactoryTag` create state for a particular session with
`forSession(sessionId)`. That prevents one conversation's memory or audit
recorder from being reused by another conversation.

The agent-loop Effect directly resolves hooks, tool orchestration, session
storage, memory factory, recorder factory, and recovery manager. The DI
migration is deliberately partial: `ProviderRegistryTag` is wired but has no
live agent-loop consumer yet; provider lookup still uses `getProvider()`.

## Layers: which implementation should we use?

A **layer** is the wiring recipe for a service. `layers.ts` is the
**composition root**—the one place that answers “which implementation does the
application use?”

```text
                 SessionStoreTag
                        ↑
AppLayerLive ───────────┘  real files under ~/.freecode
makeTestLayer() ─────────  temporary directory for a test
```

`AppLayerLive` merges the nine live services. It creates real hooks, tool
orchestration, session persistence, memory factories, recorders, and recovery
configuration. A layer reused by reference is **memoized**, meaning it is built
once even if several services need it. For example, one session-store layer
serves both `SessionStoreTag` and `SessionManagerTag`.

`makeTestLayer(overrides)` creates the same shape but makes risky parts safe:

- sessions use a temporary directory;
- memory uses in-memory storage;
- rollout recording is disabled, so tests do not write to `~/.freecode`; and
- tests can replace individual services through `overrides`.

That replacement is a **test double**: a controlled substitute, such as an
in-memory store or fake provider, that lets a test isolate one behavior.

## Runtime: using the layer

`runtime.ts` turns a complete layer into an Effect `ManagedRuntime`.

```ts
export function getAppRuntime(): AppRuntime {
  if (!appRuntime) appRuntime = ManagedRuntime.make(AppLayerLive);
  return appRuntime;
}
```

The live runtime is lazy and shared: it is created on first use, then reused by
server, CLI, eval, and autonomous-run entry points. Code runs an Effect through
it with `runPromise(...)`.

Tests use `makeRuntime(makeTestLayer(...))`. Production and tests therefore
follow the same dependency-composition path; only the supplied services differ.
`disposeAppRuntime()` and `runtime.dispose()` release runtime resources so one
test cannot leak state into the next.

## Loop health: a pure safety policy

`loop-health.ts` is different from the wiring files: it contains actual
decision logic. `createLoopHealthEvaluator()` examines the loop state and
returns one of three actions: `continue`, `warn`, or `stop`.

| Signal | Beginner meaning | First response | Escalation |
| --- | --- | --- | --- |
| Repeated tool call | the same action keeps failing or repeating | warn | stop at twice the threshold |
| Stagnant turns | several turns changed no files | warn | no separate hard-stop rule |
| Oscillation | edit, undo, then edit again | warn | stop at twice the threshold |
| Repeated reasoning | near-identical reasoning appears across turns | warn | stop at twice the threshold |
| Iteration cap | the configured maximum number of loop iterations is reached | — | stop immediately |

The warn-then-stop approach is intentional. Real coding tasks often read the
same file twice or revise a change; one suspicious signal should remind the
model to reassess, not immediately kill useful work. A repeated pattern is much
stronger evidence of a stuck loop.

The evaluator is a **pure function object**: it reads state and thresholds and
returns an action without disk, network, or UI work. That makes the policy easy
to test independently from the agent loop.

## What DI does—and does not—cover today

Before this boundary existed, testing `agent/loop.ts` could touch a real session
store unless every singleton was mocked separately. Now a test supplies
`makeTestLayer()` once and the loop receives a consistent group of test-safe
dependencies. `SessionManagerLive`, for example, automatically receives the
same session store supplied to the graph.

The migration is intentionally incomplete. The bus remains a module singleton,
and the provider-registry tag has no live consumer yet. **Dependency inversion**
is the direction of the design, while the strongest current test seam is around
agent-loop construction and session persistence.

## Interview vocabulary

- **Dependency injection (DI):** pass dependencies into code rather than
  constructing them inside the code.
- **Inversion of control (IoC):** the composition root chooses concrete
  implementations; the agent loop does not choose its own store.
- **Interface / contract:** a stable shape, such as `SessionStore`, that both a
  live implementation and a test double can satisfy.
- **Composition root:** `layers.ts`, where dependencies are assembled in one
  place.
- **Lifecycle management:** `ManagedRuntime` creates shared services and its
  disposal API releases them after a test or shutdown.
- **Memoization:** reuse one constructed dependency instead of rebuilding it
  for every consumer.
- **Pure function:** a calculation with no I/O or hidden mutation, such as the
  loop-health decision.
