# Internals

This guide explains how FreeCode works from first principles. You do not need
previous AI-agent experience: each page introduces the idea first, then shows
the real source code behind it.

At a high level, FreeCode repeats one cycle: you send a prompt; a model decides
whether it needs a tool; FreeCode checks that action is allowed and runs it; the
result returns to the model; and the cycle ends when the model has a final
answer. This repeated **agent loop** is the core pattern behind a production AI
coding harness.

## A one-minute mental model

Think of FreeCode as a careful coordinator between you, your project, and a
model. The user interface displays what is happening; `apps/core` keeps the
conversation, calls the model, runs approved tools, and records what happened.
The model never gets direct, unrestricted access to your files or shell.

### Key terms worth knowing

These are useful interview keywords, with the plain-English meaning first:

- **Agent loop:** the repeat-until-finished cycle of model decision → tool use →
  tool result → next model decision.
- **JSON-RPC:** a small request/response protocol. A client calls a named method
  such as `session.send`; core returns a result.
- **Server-Sent Events (SSE):** a one-way live update stream used by the
  browser/mobile client to receive text and tool progress as they happen.
- **Event bus / pub-sub:** an internal message channel. Subsystems publish an
  event once, and interested listeners receive it without calling each other
  directly.
- **Event sourcing / rollout log:** an append-only record of what happened in a
  run. FreeCode uses it for tracing, replay, cost analysis, and evaluation.
- **MCP (Model Context Protocol):** a standard way to add tools supplied by
  external servers.
- **Dependency injection (DI):** services are supplied through a runtime layer
  instead of being hard-coded global imports, making them easier to replace in
  tests.
- **Fail closed:** when FreeCode is unsure whether an action is safe or valid,
  it asks or blocks rather than silently allowing it.

## The thin-client boundary

TUI, VS Code, the browser/mobile client, and the desktop app are pure
presentation layers — they render and speak IPC, nothing else. A request first
reaches core's server, which starts or resumes a session and hands the work to
the agent loop. TUI and VS Code use JSON-RPC over standard input/output; the
browser/mobile client uses the same JSON-RPC methods over HTTP and receives live
updates through Server-Sent Events (SSE). The event bus publishes those updates;
it does not route requests.

That boundary means a bug fix or a new capability written once in core reaches
every client without duplicating the agent logic. It also means core can run
headlessly — in CI, `freecode eval`, or a script — with no UI code loaded. The
separate `apps/web` project is FreeCode's public website, not this coding
client. See [IPC protocol](/internals/ipc) for the wire format.

One distinction is worth keeping in mind as you read the diagram: a **session**
is the current conversation and its diagnostic event log; **memory** is a small
set of useful facts that can survive into a later session. They solve different
problems, so the diagram keeps them separate.

## The safety and design rules the codebase keeps

A handful of rules recur across every subsystem. They are also useful examples
of the trade-offs a production agent harness makes:

- **Core owns the business logic.** Frontends render and send requests; only
  `apps/core` calls providers, reads files, or executes tools. This is the
  **thin-client architecture** boundary.
- **One event egress, one bridge.** The [event bus](/internals/bus) has one
  `subscribeAll` writer per process. In simple terms: each event has one route
  out to clients, preventing accidental duplicate updates.
- **Fail closed.** An unclassified tool is treated as mutating
  ([permissions](/internals/permissions)); an unconfigured eval judge closes a
  release gate instead of passing quietly ([eval](/internals/eval)); and a
  denied tool call still leaves a trace ([agent loop](/internals/agent-loop)).
- **Dependency injection over singletons.** [Effect layers](/internals/runtime)
  supply services instead of module-level global objects, so a test can replace
  an entire dependency graph with safe test doubles.
- **A denial is observable, not silence.** A refused tool call becomes its own
  event type, `function.denied`, rather than disappearing. This keeps traces,
  evaluations, and debugging honest.
