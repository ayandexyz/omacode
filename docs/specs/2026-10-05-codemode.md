# Codemode — the model writes a script that calls tools

**Status:** Phases 0–2 built, Phase 3 measured 2026-10-05 (§6.1). **Verdict: stays
off by default** — neither measured model chooses it unprompted.
**Branch:** `feat/codemode` (spec), `feat/codemode-phase0` (Phases 0–1).
**Source:** pi's `codemode` tool (`~/Projects/githubProjects/agents/pi`,
`packages/codemode` + `packages/coding-agent/src/extensions/codemode/`, docs
`packages/coding-agent/docs/codemode.md`, landed 2026-09-29 in `8562bcf66`).
The idea and name come from Cloudflare's "Code Mode" (2025): turn tools into an
API, let the model write code against it, and return only what the code prints.

| Phase | What | Size |
| --- | --- | --- |
| 0 | Spike: pi's sandbox runs inside `pnpm build:bun`; measure the description's token cost | small |
| 1 | `codemode` tool, nested calls through the loop's full tool pipeline, off by default | medium |
| 2 | Tool discovery (`searchTools`/`describeTool`), `store`/`load` persisted in the session | small |
| 3 | `eval ab` on cost and pass rate; decide the default | small (paid) |

Non-goals: Cloudflare-style remote execution, pi's `models.classify()` /
`generateImages()` (FreeCode has no non-LLM model catalogue), pi's `mode: "only"`
(hiding the direct tools — revisit after Phase 3), a script starting a subagent,
and a script starting another script.

---

## 1. Why

Every tool call today is one model round trip, and every result enters the
transcript in full (up to the `adaptiveTruncate` budget) and stays there until
compaction. Two shapes of work pay for that:

- **Fan-out.** "Which of these 30 files import X, and how?" is 30 `read`s or a
  `grep` plus many `read`s, each a separate turn, each result kept forever.
- **Filtering.** A `bash` or MCP call whose useful part is three lines out of
  three thousand. The model has to see all of it to pick the three lines.

A script does the loop and the filtering in the sandbox and returns only the
answer:

```js
const hits = await tools.grep({ pattern: "createToolOrchestrator\\(", path: "apps/core/src" });
const files = [...new Set(hits.split("\n").map((l) => l.split(":")[0]).filter(Boolean))];
const bodies = await Promise.all(files.map((path) => tools.read({ path })));
return files.map((f, i) => `${f}: ${bodies[i].includes("permissionProfile") ? "passes profile" : "{}"}`);
```

## 2. Will it reduce token cost?

**Hypothesis, not a promise.** Phase 3 measures it, and the default stays off
until it does.

Where it saves:

1. **Fewer turns.** N sequential calls become one call. Each saved turn saves a
   full request — but at FreeCode's measured ~99% cache hit rate the re-sent
   prefix is billed as a cache read (0.1× input on Anthropic), so the saving per
   turn is smaller than "one whole context".
2. **Less transcript growth — the bigger lever.** A filtered result is a few
   hundred tokens instead of tens of thousands, and every later request carries
   the difference. This also delays compaction.
3. **Parallelism** cuts wall time, not tokens.

Where it costs:

1. **The description.** Every request carries the `codemode` tool definition.
   Cached after the first request, but it is a fixed tax on every session that
   has the tool, including ones that never use it. Measured in §3.1: ~330
   tokens (+5% on build mode's tool list) if it does not re-declare the tools,
   ~4.5k (+73%) if it does. pi cut its own by 40% in its second release for
   the same reason.
2. **Code is output.** A script is written as output tokens (≈5× the input price
   on most providers), and JSON-encoding it as a tool argument adds escapes.
3. **Failed scripts.** A wrong method name or a bad assumption about a result's
   shape is a wasted turn. Weaker models will do this more — whether MiniMax et
   al. write usable scripts is the open question Phase 3 answers.

Expected outcome: a saving on fan-out and large-output tasks, roughly neutral or
a small loss on short single-edit tasks. That is why it ships off and why the
eval suite needs fan-out cases (§6), not just the existing trajectory suite.

### 3.1 Results (2026-10-05)

**The binary carries it.** `@earendil-works/pi-codemode@1.0.2` is on npm and
pinned exact in `apps/core`. `codemode/runtime.ts` picks the wasm and worker;
`freecode __codemode-smoke` (hidden) runs one script calling one host tool, and
`scripts/smoke-codemode-binary.mjs` runs that against a compiled binary from
outside the repo. Passes on linux-x64; **macOS and Windows are untested.**

- **wasm:** shipped as a loose `quickjs.wasm` beside the binary
  (`copyQuickJSWasm` in `build-bun.mjs`), the same pattern as `web-ui/` and the
  onnx libs, so the release archive carries it with no workflow change. 637 KB,
  platform-neutral. pi instead imports the `.wasm` from a Bun-only entry file;
  FreeCode's binary bundles core's `tsc` output, where that import cannot live.
- **worker:** `apps/core/dist/codemode/worker.js` is a second `bun build`
  entrypoint. Bun roots embedded files at the entrypoints' common ancestor
  (`apps/`) under `/$bunfs/root`. **A relative specifier does not resolve** —
  `./core/…`, `./apps/core/…` and bare `core/…` all fail with `ModuleNotFound`
  from `node:worker_threads` (Bun 1.3.14); only the absolute path works. Core
  derives the root from its own `import.meta.url` (the bundle lives at that
  root), which should also cover Windows' `B:\~BUN\root` — unverified.

**The description's cost** (o200k tokenizer as a proxy, `gpt-tokenizer`; no
provider tokenizer was available offline). Built-in tools only, no MCP:

| | build mode (21 tools) | explore mode (12) |
| --- | --- | --- |
| today's tool list, JSON | 6,206 | 2,998 |
| inline declarations of every callable tool, with descriptions | +4,519 (+73%) | +2,803 (+93%) |
| inline declarations, signatures only | +2,106 (+34%) | +1,555 (+52%) |
| lean `codemode` tool def (globals + "tools.<name> takes the same args as the direct tool") | **+332 (+5%)** | **+332 (+11%)** |

So §4.7 changes: **do not inline declarations of tools the model already
has** — they are already in the request as JSON schemas, and pi's `on` mode
reaches the same conclusion. The `codemode` description says that every directly
callable tool is `tools.<name>(sameArgs)` and lists only the globals. That makes
the fixed tax in §2 ~330 tokens per request (cached after the first), not
~4.5k. Inline declarations are only for tools the model cannot see directly —
MCP tools under Phase 2's `describeTool()`.

## 4. Phase 1 — the tool

### 4.1 Shape

`tools/codemode.ts`, built with `buildTool`:

```
codemode({ script: string })
```

`script` is the body of an async function; top-level `await` and `return` work.
An optional first line `// @options: {"max_output_tokens": N, "timeout_ms": N}`
as in pi. Inside: `tools.<name>(args)`, `text()`, `console.*`, `return`,
`exit()`, `ALL_TOOLS`. Nothing else — no `fetch`, timers, `process`, modules.

pi takes raw JavaScript as the tool input (a free-form tool). The AI SDK path is
JSON tool calls, so FreeCode takes `{ script }`. Revisit only if Phase 3 shows
escaping errors.

### 4.2 Nested calls go through `executeTool` — the load-bearing rule

Permissions, PreToolUse/PostToolUse hooks, the role allowlist, mode enforcement,
the unattended envelope and every `denyToolCall()` site live in
`AgentLoop.executeTool()` (`agent/loop.ts:2967`), **not** in the orchestrator. A
nested call that went to `orchestrator.execute()` directly would bypass all of
them, and codemode would become a way out of plan mode, out of a deny rule, and
out of `freecode night`'s envelope.

So:

- `ToolContext` gets `callTool?: NestedToolCaller`, set by `executeTool` only
  for a top-level `codemode` call while codemode is enabled, bound to
  `AgentLoop.nestedToolCaller(parent)` → `this.executeTool({ id: \`${parent.id}.${n}\`, tool, args }, parent.id)`.
- Calls that are not concurrency-safe (`isConcurrencySafeCall`, the batcher's
  own test) run one at a time, so a `Promise.all` over writes cannot race two
  permission prompts or two edits of one file. Safe ones run in parallel.
- A nested destructive call marks the run as having changed files
  (`noteMutation`, shared with the batch path), so the verifier still fires.
- The sandbox's host functions are thin wrappers over `ctx.callTool`. A
  `ToolResult` with `error` rejects with that text; a denial rejects with the
  denial message, so the script (and then the model) sees why.
- A nested call that asks for permission prompts the user exactly like a direct
  one. The script waits. This can be noisy (a loop of 20 `bash` calls is 20
  prompts unless the user picks "always"); that is the correct behaviour and the
  cost of not building a bypass.

### 4.3 Which tools a script can call

The same list `getToolDefs(this.state.agentMode)` offers the model, minus:
`codemode` (no recursion), `finish_iteration`, `agent`, `agent_send`,
`agent_stop`, `monitor`. MCP tools are included. A tool the mode does not offer
is therefore **absent** from the script's `tools`, and the sandbox reports
"does not exist" before the loop is ever asked — the loop's check (§4.2) is the
second layer, for tools that are offered but denied by a rule, hook or role. Identifiers follow pi:
characters invalid in a JS identifier become `_`
(`mcp__dev-radius__search` → `tools.mcp__dev_radius__search`), and the
original name also works as `tools["mcp__dev-radius__search"]`.

### 4.4 What a nested call resolves to

The orchestrator truncates the model's view (`adaptiveTruncate`) after putting
the full text in the `OutputStore`. A script should see the **full** output — its
whole point is to filter it — so the host wrapper reads the stored full text by
call id, capped at 1 MiB (head + tail, as pi does for `bash`). Phase 1 resolves
every tool to a string; structured `bash` results (`{ output, exit_code }`) are a
Phase 2 refinement if scripts need them.

### 4.5 What the model sees

`Script completed` / `Script failed` + wall time + output, capped by
`max_output_tokens` (default 10,000), then the codemode result goes through the
normal orchestrator path like any tool result — `OutputStore` put, truncation,
`output` paging. Calls made before a failure are not undone; that is stated in
the description.

### 4.6 Registration checklist (CLAUDE.md "Adding a tool")

- `tools/index.ts` — always registered; `defs-cache.ts` keeps it out of the
  shared list (`CODEMODE_TOOL`) and `withCodemode()` appends it for a loop that
  has it enabled, so a session without it sends the same tool list as before.
- `permission/mode-policy.ts` — add `codemode` to `READONLY_TOOLS`. It has no
  capability of its own; every nested call is gated individually by §4.2, so
  offering it in plan/explore is safe and a script there can only read.
- `permission/rules.ts` — not a path or URL tool; rules match the nested calls.
- `permission/suggest.ts` — `DISPLAY_NAMES.codemode = "Codemode"`.

### 4.7 Prompt cache

The description is fixed text: the globals, plus one line saying every
directly callable tool is `tools.<name>(sameArgs)`. It inlines **no** tool
declarations (§3.1: that would cost ~4.5k tokens in build mode for schemas the
request already carries). It therefore does not change when the tool set
changes — not on a mode switch, not when an MCP server connects. MCP tools are
reachable by name through `ALL_TOOLS`, and their declarations through Phase 2's
`describeTool()`.

### 4.8 Trace, rollout, UI

- A nested `function.call` carries `parentCallId` (the codemode call's id) and
  `ToolSpan.parentCallId` carries it through the fold. `function.output` pairs by
  `callId` as before, so it needs nothing new.
- `Trace.toolSpans` means "tools that ran"; nested calls ran, so they are tool
  spans. Consequence for evals: `expectTool("grep")` and `forbidTools` see a
  script's calls the same as direct ones. `expectFirstToolIn` **looks through**
  a leading codemode span to the first call its script made, unless the case
  names `codemode` itself — a script is a vehicle, not a move, and scoring it
  as the opening move would make every trajectory case fail under `eval ab`
  for a reason unrelated to the question the case asks.
- No `codemode.script` event: the nested-call count is the number of spans with
  that `parentCallId`, and ok/failed is the codemode span's `failed`. The script
  text is in the codemode `function.call` args, as a `bash` command is.
- Usage: nested tools are not model calls, so cost is unchanged.
- Frontends get the nested `tool_start` / `tool_complete` events as they do
  today. A `parentToolCallId` on `StreamEvent` (for indentation) is optional and
  can follow.

### 4.9 Enablement

Off by default. `codemode.enabled` in settings, `FREECODE_CODEMODE=1|0` (env
beats files, like the signal gates). Subagents get it when the parent has it;
a role's `tools` allowlist must name `codemode` to offer it.

### 4.10 Built (2026-10-05)

`tools/codemode.ts`, `codemode/{settings,format}.ts`, the loop wiring in
`agent/loop.ts` (`codemodeEnabled`, `nestedToolCaller`, `noteMutation`).
`agent/codemode-loop.test.ts` runs the real loop with a fake provider: a mode
hides `write` from a script; a `Read(./secret.txt)` deny rule refuses a script's
read with `function.denied` (source `rule`) and the content never reaches the
result; nested calls carry `parentCallId` and see output past the model's 30 KB
cap; disabled means not offered and refused. Not yet run against a real model.

Known gaps:

- `context/breakdown.ts` (the `/context` view) counts the tool list without
  codemode, so it under-reports by ~420 tokens when codemode is on.
- Images a script produces are counted, not returned (`[N image(s) omitted]`).
- A nested call still running when its script ends is not cancelled (pi cancels
  it); it finishes on its own and its result is discarded.

## 5. Phase 2 — discovery and store

- `searchTools(query, { limit })` (BM25 — reuse `memory/bm25.ts`) and
  `describeTool(name)` returning the TypeScript declaration, so non-inlined tools
  (MCP) are usable without growing the description.
- `store(key, value)` / `load(key)`: small JSON across `codemode` calls. Writes
  are kept only when the script succeeds, and are appended to the session store
  so resume keeps them and `/tree` branches see only their own path (same shape
  as pi's `codemode-store` entries). Limits as pi: 256 KiB per value, 1 MiB total.

### 5.1 Built (2026-10-05)

- `codemode/discovery.ts`: `searchTools` reuses `memory/bm25.ts` (a tool is
  shaped like a memory entry: a name and a description), with a name-substring
  fallback for terms BM25 drops (`ls`, `lsp`). `describeTool` is pi-codemode's
  `renderToolSample`. Both are sandbox globals over the same list as `tools`.
- Store: a successful script that changed the map returns the whole map in its
  result metadata; `appendToolMessage` writes it onto the persisted tool part
  (`SerializedMessage.parts[].codemodeStore`), and the next codemode call loads
  the latest one on the active path (`loadCodemodeStore`). That gives resume
  and `/tree` isolation without a new entry type — `codemode-loop.test.ts`
  branches back past a write and reads the older value. pi's per-value and total
  size limits are enforced by the sandbox itself.
- **Gap:** compaction trims the message log; once every codemode message that
  carried a snapshot is trimmed, the store is empty again. Acceptable for the
  store's stated purpose (ids, cursors); re-stamping the snapshot onto the
  compaction summary is the fix if it matters.
- The description is now **417 tokens** (+6.7% on build mode's tool list),
  up from 332 for the two added lines.

## 6. Phase 3 — measure and decide

New eval cases (`evals/codemode.jsonl`) shaped for the fan-out and filtering the
feature exists for, e.g. "count call sites of X per package", "which tests in
`tools/` mention Y", a large-output `bash` whose answer is one line. Then:

```
pnpm eval ab codemode --baseline env:FREECODE_CODEMODE=0 --candidate env:FREECODE_CODEMODE=1 --trials 5 \
  --hypothesis "codemode cuts cost per passed task on fan-out cases without lowering pass rate"
pnpm eval ab trajectory --baseline env:FREECODE_CODEMODE=0 --candidate env:FREECODE_CODEMODE=1 --trials 5
```

On at least the default provider and one cheaper model (MiniMax). Read cost per
passed task, turns, and input tokens, not just pass rate.

Flip the default only if: no pass-rate regression on `trajectory` and `coding`,
and a clear cost-per-passed-task saving on `codemode`. Otherwise it stays an
opt-in for users with heavy MCP or fan-out work, and the result is recorded here.

### 6.1 Results (2026-10-05, ledger `evals/experiments.jsonl`)

| Run | Pass (off → on) | Cost (off → on) | codemode calls |
| --- | --- | --- | --- |
| `codemode` × MiniMax-M3, 5 trials (`2026-10-04-codemode-1`) | 20/20 → 20/20 | $0.175 → $0.222 (+27%) | **0** of 20 trials |
| `codemode` × gemini-3.6-flash, 3 trials (`…-codemode-2`) | 12/12 → 12/12 | $0.462 → $0.559 (+21%) | **0** of 12 |
| `trajectory` × MiniMax-M3, 3 trials (`…-trajectory-1`) | 29 unchanged-pass, 1 unchanged-fail, 1 inconclusive | $0.918 → $0.623 (−32%, noise) | **0** |

Reading it:

- **Neither model reaches for codemode on its own**, even on cases built for
  it. They solve fan-out with a `bash` pipeline or a run of direct `read`s, and
  both pass every case either way. So the measured cost delta is the tool
  definition carried on every request (~420 tokens, §5.1) plus run-to-run
  noise — not codemode doing anything. The trajectory side's −32% is the same
  noise in the other direction (one baseline trial looped: repeated calls
  12 → 0); a tool that was never called cannot have caused it.
- **Offering it does not disturb routing**: the trajectory suite is unchanged
  but for one inconclusive case.
- **It works when asked.** A live `freecode run` telling the model to use it:
  gemini-3.6-flash wrote one script doing `glob` + 6 parallel `read`s (traced as
  7 nested calls) and answered correctly. MiniMax-M3 wrote `glob(...).map(...)`
  on the string result twice and ran out of turns; the description now says
  every call resolves to a string and names the reserved globals (commit
  `57f40fd0`), which did not fix MiniMax on the retry.

**Decision:** keep codemode off by default and opt-in. Re-measure when a model
in use is one that writes scripts well unprompted (Anthropic/OpenAI frontier
models are the obvious next run; not measured here), or if `mode: "only"`
(hiding the direct tools, pi's other setting) is ever built — that is the only
configuration in which an unwilling model would actually use it.

## 7. Risks

- **Bypass.** Any nested path that skips `executeTool` is a security bug. Test:
  in `explore` mode a script calling `tools.write` is denied with the mode
  message and produces a `function.denied` event.
- **Weak models.** Bad scripts cost a turn each. Phase 3 measures it per model.
- **Prompt storms.** See §4.2. Not mitigated on purpose.
- **Worker in the Bun binary.** Phase 0 exists for this.
- **Dependency.** A young package from another project; pin the exact version.
